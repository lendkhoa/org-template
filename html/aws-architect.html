1. How to Use This Guide

  • Each domain follows the same structure: Patterns → Buzzword Matrix → Tricky Scenarios → Diagram → Docs.
  • The exam rarely tests "what is service X." It tests which service combination satisfies constraints like cost, RTO/RPO, latency, and operational overhead. Train yourself to underline the constraint words in every question.
  • Golden elimination rule: if two answers are technically valid, the one that is more managed, more AWS-native, and matches the stated constraint (cheapest, fastest, least ops) wins.
  • Distractors usually fail for one of five reasons: (1) wrong scope (AZ vs Region vs Global), (2) wrong consistency/durability guarantee, (3) violates the cost or ops constraint, (4) solves availability when the question asks scalability (or vice versa), (5) legacy/self-managed option when a managed one exists.

2. Domain 1: Design Secure Architectures [30%]

2.1. Core Architectural Patterns & Service Pairings

2.1.1. Edge protection for static/dynamic content

  • S3 + CloudFront + Origin Access Control (OAC) + WAF: Bucket stays private; only CloudFront can read it via OAC (the modern replacement for OAI). WAF attaches to the CloudFront distribution for L7 filtering (SQLi, XSS, geo-match, rate-based rules). Shield Standard is automatic; Shield Advanced adds DDoS cost protection + DRT support.
  • ALB + WAF + Cognito: WAF Web ACL on the ALB; ALB can natively authenticate users against Cognito User Pools before traffic reaches targets.

2.1.2. Private connectivity (no internet traversal)

  • Gateway VPC Endpoint (S3 / DynamoDB): Free, route-table based, S3 and DynamoDB only.
  • Interface VPC Endpoint (PrivateLink): ENI-based, hourly + data cost, works for most other AWS services (SQS, SNS, KMS, Secrets Manager, SSM…) and third-party/SaaS endpoint services.
  • Site-to-Site VPN over Direct Connect: DX alone is not encrypted; layering an IPsec VPN over DX gives private + encrypted.
  • Transit Gateway + DX Gateway: Hub-and-spoke for many VPCs/on-prem networks; replaces unscalable VPC-peering meshes.

2.1.3. Identity & access

  • IAM Roles > IAM Users/keys: EC2 instance profiles, ECS task roles, Lambda execution roles. Cross-account access = role in target account + sts:AssumeRole trust policy (never share access keys).
  • Cognito User Pools = authentication (sign-in, JWT). Cognito Identity Pools = authorization (exchange identity for temporary AWS credentials).
  • IAM Identity Center (SSO): workforce federation to multiple accounts in an Organization.
  • SCPs (Service Control Policies): Organization-level guardrails — they set the maximum permission boundary; they never grant permissions.

2.1.4. Data protection

  • SSE-S3 (AWS-managed keys), SSE-KMS (auditable via CloudTrail, key policies, can enforce with bucket policy condition s3:x-amz-server-side-encryption), SSE-C (customer supplies key per request), client-side encryption (AWS never sees plaintext).
  • KMS multi-Region keys: encrypt in one Region, decrypt in another (DR-friendly).
  • Secrets Manager: secrets with automatic rotation (native RDS/Aurora/Redshift/DocumentDB rotation). SSM Parameter Store: config values, free standard tier, no native rotation.
  • Macie: discovers PII/sensitive data in S3. GuardDuty: threat detection (VPC Flow Logs, DNS, CloudTrail analysis). Inspector: vulnerability scanning of EC2/ECR/Lambda. Security Hub: aggregates findings.

2.1.5. Network segmentation

  • Security Groups: stateful, allow-rules only, instance/ENI level.
  • NACLs: stateless (need explicit inbound AND outbound rules, mind ephemeral ports), allow + deny, subnet level. Use NACL deny rules to block a specific IP.

2.3. Tricky Scenarios & Distractor Analysis

2.3.1. Scenario 1: Private S3 origin

  1. Requirement: A company serves a static site from S3 through CloudFront. Security mandates the bucket must not be publicly accessible and objects must only be retrievable through CloudFront, with minimal management.
  2. Correct Architecture: Keep Block Public Access ON. Create an Origin Access Control (OAC) on the CloudFront distribution and add a bucket policy allowing s3:GetObject only when the request comes from that distribution (AWS:SourceArn condition, principal cloudfront.amazonaws.com).
  3. Why Distractors Fail:
    • Make the bucket public with a website endpoint: violates the "not public" requirement; S3 website endpoints also don't support OAC or HTTPS to origin.
    • Use signed URLs for every object: solves user-level authorization, not origin locking, and adds heavy operational overhead.
    • Use OAI: technically works but is legacy; when both appear, OAC is the intended answer (supports SSE-KMS, all Regions, POST/PUT).

2.3.2. Scenario 2: Private subnet → S3, cheapest and most secure

  1. Requirement: EC2 instances in private subnets upload logs to S3. Traffic must not traverse the internet, and the solution should minimize cost.
  2. Correct Architecture: Gateway VPC Endpoint for S3 + route table entry + (optionally) endpoint policy / bucket policy with aws:sourceVpce condition.
  3. Why Distractors Fail:
    • NAT Gateway: traffic technically leaves via AWS's network to the public S3 endpoint, costs ~$0.045/GB processing + hourly — fails both constraints.
    • Interface endpoint for S3: works, but incurs hourly + per-GB charges; only preferred when on-prem hosts must reach S3 privately over DX/VPN (gateway endpoints aren't reachable from outside the VPC).
    • VPC peering to an "S3 VPC": S3 doesn't live in a customer VPC; nonsense distractor.

2.3.3. Scenario 3: Third-party auditor account access

  1. Requirement: An external auditing firm needs read-only access to CloudTrail logs in your account. Grant access securely.
  2. Correct Architecture: Create an IAM role with a read-only policy scoped to the log bucket/CloudTrail, trust policy naming the auditor's AWS account, and require an External ID to prevent the confused-deputy problem. Auditor assumes the role via STS.
  3. Why Distractors Fail:
    • Create an IAM user and email them the access keys: long-lived credentials, no rotation, violates least privilege best practice — always wrong on this exam.
    • Make the log bucket public with a hard-to-guess name: security through obscurity; instant elimination.
    • Cross-account role without External ID: a partial answer; when External ID appears as an option for third parties, pick it.

3. Domain 2: Design Resilient Architectures [26%]

3.1. Core Architectural Patterns & Service Pairings

3.1.1. The canonical 3-tier HA stack

  • Route 53 → ALB (multi-AZ by design) → Auto Scaling Group across ≥2 AZs → RDS Multi-AZ.
  • ASG health checks should use ELB health checks (not just EC2 status) so app-level failures trigger replacement.
  • Session state moved off instances → ElastiCache (Redis) or DynamoDB so instances are stateless/disposable.

3.1.2. Database resilience vocabulary (memorize this split)

  • RDS Multi-AZ: synchronous standby, automatic failover (~60–120s), same endpoint, standby NOT readable (except Multi-AZ DB Cluster with 2 readable standbys). Purpose: availability.
  • RDS Read Replicas: asynchronous, readable, can be cross-Region, no automatic failover (manual promotion). Purpose: read scalability (+ manual DR).
  • Aurora: 6 copies across 3 AZs, up to 15 replicas, replicas ARE the failover targets (~30s), Reader/Writer endpoints.
  • Aurora Global Database: <1s cross-Region replication lag, RPO ~1s, RTO <1 min (managed failover) — the answer to "lowest RTO/RPO across Regions for relational data."
  • DynamoDB Global Tables: multi-Region, multi-active read/write — the answer for NoSQL active-active.

3.1.3. Decoupling & buffering

  • SQS between tiers: absorbs spikes, retries via visibility timeout, DLQ for poison messages. Standard = at-least-once, unordered; FIFO = exactly-once, ordered, 300/3000 msg/s.
  • SNS → SQS fan-out: one event, many independent consumers.
  • EventBridge: event routing with filtering, SaaS/AWS-service events, scheduling.

3.1.4. Disaster recovery ladder (cost ↑ as RTO/RPO ↓)

  1. Backup & Restore: hours RTO — cheapest.
  2. Pilot Light: core (DB replicated) always on, app servers off — RTO tens of minutes.
  3. Warm Standby: full stack running scaled-down — RTO minutes.
  4. Multi-site Active-Active: Route 53 latency/weighted routing, both Regions serve traffic — RTO ~0, most expensive.
  5. Route 53 failover routing + health checks drives DNS-level failover for options 2–3. S3 Cross-Region Replication and AWS Backup underpin data-layer DR.

3.1.5. Storage resilience

  • EFS: Regional (multi-AZ) by default, NFS, Linux, thousands of concurrent clients. One Zone class is cheaper but single-AZ.
  • EBS: locked to one AZ — "resilient shared storage across AZs" is never EBS. Snapshots (to S3) are the portability mechanism.
  • S3: 11 nines durability; Standard/IA are multi-AZ; One Zone-IA is not.

3.3. Tricky Scenarios & Distractor Analysis

3.3.1. Scenario 1: "HA for RDS" — the classic trap

  1. Requirement: A MySQL RDS database must remain available if an AZ fails, with automatic failover and no application connection-string changes.
  2. Correct Architecture: Enable Multi-AZ. Synchronous standby in another AZ; on failure, DNS of the same endpoint flips to the standby automatically.
  3. Why Distractors Fail:
    • Create a Read Replica in another AZ: replication is asynchronous (possible data loss) and failover is manual (promote + repoint app). Read replicas = performance/DR, not HA.
    • Take frequent snapshots: that's backup/restore — RTO in hours, not automatic.
    • Migrate to DynamoDB: changing the data model is never the answer when a checkbox feature exists.

3.3.2. Scenario 2: Order processing that must never drop requests

  1. Requirement: A checkout flow spikes 10x during sales. Orders must never be lost, must be processed exactly once and in the order received per customer.
  2. Correct Architecture: Web tier → SQS FIFO queue (MessageGroupId = customerId for per-customer ordering, deduplication ID for exactly-once) → ASG of workers scaling on ApproximateNumberOfMessagesVisible, with a DLQ for poison messages.
  3. Why Distractors Fail:
    • SQS Standard: at-least-once + best-effort ordering — violates both stated guarantees.
    • SNS direct to consumers: no buffering/persistence if consumers are down; messages lost.
    • Kinesis Data Streams: ordered per shard and replayable, but dedup/exactly-once consumer logic is on you; FIFO matches the requirement with less overhead. (Kinesis wins when the keyword is "real-time analytics," "multiple consumers reading same stream," or "replay.")
    • Scale the web tier bigger: throws money at the symptom; still tightly coupled.

3.3.3. Scenario 3: Picking the DR strategy

  1. Requirement: A business-critical app needs RTO ≤ 15 minutes and RPO ≤ 5 minutes in a second Region, while minimizing steady-state cost.
  2. Correct Architecture: Warm Standby — scaled-down full environment in the DR Region, continuous data replication (e.g., Aurora Global DB or RDS cross-Region read replica + DMS/CRR for other data), Route 53 health-check failover; scale up ASG on failover.
  3. Why Distractors Fail:
    • Backup & Restore: RTO measured in hours — fails the 15-minute target.
    • Pilot Light: app servers must be launched from AMIs at failover time — usually quoted as "tens of minutes"; risky for a 15-min RTO. (If the question says RTO 30–60 min and "lowest cost," pilot light wins.)
    • Active-Active multi-site: meets RTO/RPO easily but violates "minimize cost." The exam wants the cheapest option that still meets the stated RTO/RPO.

4. Domain 3: Design High-Performing Architectures [24%]

4.1. Core Architectural Patterns & Service Pairings

4.1.1. Caching ladder (edge → app → data)

  • CloudFront: cache static + dynamic content at edge; pairs with S3 (static) and ALB/API Gateway (dynamic).
  • Global Accelerator: NOT a cache — anycast static IPs + AWS backbone routing for TCP/UDP, non-HTTP workloads (gaming, VoIP), instant Regional failover, "static IP" requirement.
  • ElastiCache Redis: app-level cache, session store, leaderboards (sorted sets), pub/sub, replication + persistence. Memcached: simple, multi-threaded, no persistence/replication.
  • DAX: transparent DynamoDB cache, microsecond reads, zero code change for the DynamoDB API. ElastiCache in front of DynamoDB requires app changes — DAX wins when "no application changes."

4.1.2. Database right-sizing

  • DynamoDB: single-digit-ms at any scale, on-demand vs provisioned+auto scaling; Global Tables for multi-Region; Streams for CDC.
  • Aurora: up to 15 low-latency replicas, reader endpoint load balancing; Aurora Serverless v2 for spiky/unpredictable relational load.
  • RDS read replicas: scale reads; route analytics/BI to a replica so it never touches the primary.
  • Redshift: OLAP warehouse, columnar; Redshift Spectrum / Athena to query S3 directly (Athena = serverless, per-TB-scanned, "query logs in S3 with SQL").
  • OpenSearch: full-text search, log analytics dashboards.

4.1.3. Storage performance

  • EBS gp3: baseline 3,000 IOPS/125 MBps, provision IOPS/throughput independently of size — default choice, cheaper than gp2.
  • io1/io2 Block Express: >16,000 IOPS, sub-ms, Multi-Attach capable, mission-critical DBs.
  • Instance Store: highest IOPS (NVMe, millions), ephemeral — cache/scratch/buffer only.
  • EFS: elastic throughput modes; FSx for Lustre: HPC/ML, hundreds of GBps, native S3 integration ("process S3 data with high-performance POSIX FS"); FSx for Windows: SMB + Active Directory; FSx for NetApp ONTAP: multi-protocol NFS+SMB.
  • S3 performance: 3,500 PUT / 5,500 GET per second per prefix — parallelize with prefixes; multipart upload for >100 MB; Transfer Acceleration for long-distance uploads into one bucket.

4.1.4. Network performance

  • Enhanced networking (ENA), placement groups: Cluster (low latency, same rack — HPC), Spread (isolate critical instances), Partition (distributed systems like Kafka/HDFS).
  • NLB: millions of req/s, static IP per AZ, ultra-low latency L4; ALB: L7 routing (path/host/header).

4.1.5. Streaming & ingestion

  • Kinesis Data Streams: real-time, ms latency, replay, multiple consumers, shard-based.
  • Data Firehose: near-real-time (buffered) delivery to S3/Redshift/OpenSearch — zero administration, no replay. "Load streaming data into S3 with least effort" = Firehose.
  • MSK: when the requirement literally says Kafka.

4.3. Tricky Scenarios & Distractor Analysis

4.3.1. Scenario 1: CloudFront vs Global Accelerator

  1. Requirement: A multiplayer game uses custom UDP on EC2 behind NLBs in two Regions. Global players report high latency and the client must connect to fixed IPs allow-listed by corporate firewalls.
  2. Correct Architecture: AWS Global Accelerator in front of the NLBs — two static anycast IPs, traffic enters the AWS backbone at the nearest edge, automatic health-based Regional failover, full UDP support.
  3. Why Distractors Fail:
    • CloudFront: HTTP/HTTPS only, no UDP, IPs are not static — fails two hard requirements. (CloudFront wins when the content is cacheable web content.)
    • Route 53 latency routing alone: DNS-based, subject to client TTL caching, still traverses public internet, IPs change.
    • Third NLB in another Region: doesn't address global routing or static IPs.

4.3.2. Scenario 2: Read-heavy DynamoDB with a caching constraint

  1. Requirement: A product-catalog API on DynamoDB suffers from read hot spots during flash sales. Reads must drop to microseconds without modifying application code (app uses the standard DynamoDB SDK).
  2. Correct Architecture: DynamoDB Accelerator (DAX) cluster; point the SDK endpoint at DAX — API-compatible write-through/read-through cache.
  3. Why Distractors Fail:
    • ElastiCache Redis: requires writing cache-aside logic (check cache → fall back to DB → populate) — violates "no code changes."
    • Increase RCUs or switch to on-demand: raises the cost ceiling but latency stays single-digit milliseconds, not microseconds.
    • Global Tables: multi-Region replication solves geography, not per-item read latency.

4.3.3. Scenario 3: Ad-hoc SQL on logs in S3

  1. Requirement: Analysts need occasional SQL queries over TBs of JSON/CSV logs already in S3, with minimal infrastructure and cost tied to usage.
  2. Correct Architecture: Athena with a Glue crawler/Data Catalog; convert to Parquet + partition by date to cut per-query scan cost dramatically.
  3. Why Distractors Fail:
    • Redshift cluster + COPY: always-on warehouse cost + ETL overhead for "occasional" queries; Redshift is right for constant, complex BI workloads.
    • RDS + import scripts: relational store isn't built for TB-scale scans; heavy ops.
    • OpenSearch: great for full-text/log dashboards, but the ask is ad-hoc SQL, and cluster management violates "minimal infrastructure."

5. Domain 4: Design Cost-Optimized Architectures [20%]

5.1. Core Architectural Patterns & Service Pairings

5.1.1. Compute purchasing ladder

  • On-Demand: baseline, unpredictable short-term.
  • Savings Plans / Reserved Instances (1–3 yr): steady-state 24/7 workloads (~up to 72% off). Compute Savings Plans = most flexible (EC2 + Fargate + Lambda).
  • Spot (~up to 90% off): fault-tolerant, interruptible — batch, CI, big data, stateless workers. 2-minute interruption notice. Never for databases or stateful single instances.
  • Mixed ASG pattern: baseline capacity on RIs/Savings Plans + burst on Spot (capacity-optimized allocation).
  • Lambda/Fargate: pay-per-use — wins when workload is idle most of the time ("runs a few minutes per day/hour").

5.1.2. S3 storage class ladder (know retrieval semantics cold)

Class Retrieval Use case / trap
Standard ms Hot data
Intelligent-Tiering ms Unknown/changing access patterns, no retrieval fees
Standard-IA ms Infrequent but immediate access; 30-day min
One Zone-IA ms Re-creatable data only (single AZ!)
Glacier Instant Retrieval ms Archive accessed ~quarterly, needs instant access
Glacier Flexible minutes–hours (1–12h) Archive, retrieval within hours OK; 90-day min
Glacier Deep Archive hours (12–48h) Compliance/7-10yr retention, cheapest; 180-day min
  • Lifecycle policies automate transitions + expire old versions/incomplete multipart uploads.

5.1.3. Network cost traps

  • NAT Gateway: hourly + per-GB — replace S3/DynamoDB traffic with a free Gateway VPC Endpoint.
  • Cross-AZ data transfer costs money; same-AZ is free — but don't sacrifice HA for it unless the question says so.
  • CloudFront egress is cheaper than S3/EC2 direct egress and has free origin fetches — "reduce S3 data-transfer cost for popular content" = CloudFront.
  • One NAT Gateway per AZ = HA; a single shared NAT GW = cheaper but an AZ-failure risk — the question's priority (cost vs resilience) decides.

5.1.4. Database & analytics cost

  • Aurora Serverless v2: intermittent/unpredictable workloads (dev/test, spiky SaaS).
  • Stop RDS dev/test instances off-hours (Instance Scheduler); RDS storage still billed.
  • DynamoDB on-demand for spiky/unknown traffic; provisioned + auto scaling for steady traffic (cheaper at scale).
  • Athena over Redshift for occasional queries; S3 + Athena over keeping data in expensive stores.

5.1.5. Visibility & governance

  • Cost Explorer (analyze + RI/SP recommendations), AWS Budgets (alerts/actions), Cost & Usage Report (detailed, to S3), Compute Optimizer (right-sizing ML recommendations), Trusted Advisor (idle resources, underutilized checks), cost allocation tags per team/project.

5.3. Tricky Scenarios & Distractor Analysis

5.3.1. Scenario 1: The lifecycle-policy compliance trap

  1. Requirement: Regulatory documents are uploaded daily, frequently accessed for 30 days, occasionally (but immediately) needed for 6 months, then retained 7 years and retrieved at most once a year with 24 hours' notice.
  2. Correct Architecture: Lifecycle policy — S3 Standard (0–30d) → Standard-IA (30d–180d) → Glacier Deep Archive (180d–7y, expiration after). Deep Archive's 12h standard retrieval fits "24 hours' notice."
  3. Why Distractors Fail:
    • Straight to Glacier Flexible at day 30: retrieval takes minutes-to-hours — fails "immediately needed" during months 1–6.
    • Glacier Instant Retrieval for the 7-year tier: works functionally but costs ~4x Deep Archive; "at most once a year, 24h notice" signals the cheapest tier.
    • One Zone-IA for compliance docs: single-AZ storage for irreplaceable regulated data — resilience fail.
    • Intelligent-Tiering: reasonable if the pattern were "unknown," but the pattern is explicitly known — a defined lifecycle is cheaper (no monitoring fee).

5.3.2. Scenario 2: The $10k NAT Gateway bill

  1. Requirement: Private-subnet EC2 fleet moves ~50 TB/month to S3 via a NAT Gateway. Reduce cost with no impact on functionality.
  2. Correct Architecture: Add a Gateway VPC Endpoint for S3 and update private route tables — S3 traffic bypasses NAT entirely; endpoint is free with no per-GB charge.
  3. Why Distractors Fail:
    • Interface endpoint for S3: works but adds hourly + per-GB PrivateLink charges — not the cheapest when a gateway endpoint exists.
    • Bigger/multiple NAT Gateways: NAT pricing is per-GB processed; scaling it changes nothing.
    • Move instances to public subnets with public IPs: removes NAT cost but changes security posture — "no impact" is violated; instant red flag.

5.3.3. Scenario 3: Spot vs everything else

  1. Requirement: Nightly video-transcoding jobs take 4–6 hours, can be checkpointed/restarted, and must run at the lowest possible compute cost.
  2. Correct Architecture: Spot Instances (via ASG mixed-instances policy or AWS Batch with Spot), diversified across instance types/AZs, checkpoint progress to S3 so 2-minute interruptions are harmless.
  3. Why Distractors Fail:
    • Reserved Instances: commit to 24/7 pricing for a job that runs ~25% of the day and tolerates interruption — Spot is far cheaper.
    • On-Demand with scheduled scaling: better than always-on, but ignores the interruption tolerance the question deliberately gave you (that phrase is the Spot signal).
    • Lambda: 15-minute max execution — disqualified for multi-hour jobs.

6. Cross-Domain Rapid-Fire Elimination Table

If the question says… Immediately eliminate…
"Least operational overhead" Anything self-managed on EC2 (self-hosted Kafka, MySQL…)
"No application code changes" Cache-aside ElastiCache, custom proxies
"Interruption-tolerant" On-Demand/RI as the "cheapest" answer (it's Spot)
"Automatic failover" (RDS) Read Replicas as the HA answer
"UDP" or "static IP" CloudFront
"Shared storage across AZs" EBS
"Exactly-once, ordered" SQS Standard, SNS alone
"Access S3 privately at no extra cost" NAT Gateway, Interface endpoint
"Encrypt + audit key usage" SSE-S3 (pick SSE-KMS)
"Job runs > 15 minutes" Lambda
"Third-party cross-account access" IAM users with shared keys
"Cheapest archive, retrieval in hours is fine" Glacier Instant Retrieval, Standard-IA
