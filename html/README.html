Starter template for exporting Org-mode files to HTML with a customized readtheorg theme. Copy this folder wherever a new note needs styled HTML export.

1. Structure

Path Purpose
template.org Starter file: standard preamble + SETUPFILE include
theme-readtheorg.setup HTMLHEAD include: wires up all CSS/JS below
org-themes/lib/js/ jquery, bootstrap, stickytableheaders (theme deps)
org-themes/readtheorg_theme/css/ htmlize.css (syntax colors), readtheorg.css (layout)
org-themes/readtheorg_theme/js/ readtheorg.js (TOC behavior)
Makefile make export builds all .org files into html/
githooks/pre-commit Runs make export and stages html/ before every commit; enable with make install-hooks
html/ Generated output: exported HTML + a copy of org-themes/ alongside it
wrangler.toml Tells Cloudflare's Worker build to serve static assets from html/

html/ is generated output — regenerate it with make export, don't hand-edit anything inside it.

2. Customizations vs. the stock readtheorg theme

  • Collapsible TOC sidebar: a hamburger button toggles the left table-of-contents; state persists per-browser via localStorage (readtheorg.css / readtheorg.js).
  • Legible code blocks: pre.src=/.codeblock= always render with a dark (Monokai-matching) background, since Org's exported syntax-highlight colors are baked in as inline styles tuned for a dark background (readtheorg.css).
  • Page-wide dark mode toggle: template.org embeds the darkmode-js CDN widget (bottom-right button) for toggling the whole page between light/dark.

3. Usage

  1. Copy this folder to the new note's location.
  2. Rename/edit template.org (update #+TITLE, write content).
  3. Export to HTML:
    • All files at once: make export — finds every .org file (skipping org-themes/), exports each with Emacs, and collects the results plus a copy of org-themes/ into html/ so the CSS/JS paths still resolve.
    • make clean removes html/.

    • A single file, without the Makefile: C-c C-e h h in Emacs, or from the shell: 

      emacs --batch template.org -f org-html-export-to-html
  4. Optional: make install-hooks points git at githooks/, so every commit runs make export and stages html/ automatically — no more forgetting to regenerate it before pushing.

All paths in theme-readtheorg.setup are relative to the .org file, so keep the org-themes/ folder alongside it when exporting by hand.

4. Deployment (Cloudflare Workers Git integration + GitHub SSO)

The Cloudflare dashboard's "Create a Worker" → "Import a repository" flow deploys straight from GitHub — no separate CI config in this repo. Point it at lendkhoa/org-template and use:

  • Build command: leave empty. Cloudflare's build container runs as a non-root user with no apt-get access, so Emacs can't be installed there — make export has to happen locally instead (see Usage above).
  • Deploy command: npx wrangler deploy (default). Reads wrangler.toml at the repo root, which declares html/ as the static assets directory and org-template as the Worker/project name.

Because there's no build step, html/ must be regenerated and committed locally (make export, then git add html/) before pushing — Cloudflare only deploys whatever is already checked into html/ at the pushed commit. Every push to the connected branch (main) triggers a redeploy of that content — no GitHub Actions workflow involved.

4.1. One-time Cloudflare setup

  1. Run the wizard (Workers & Pages → Create → Import a repository), selecting lendkhoa/org-template and entering the build/deploy commands above.
  2. Protect with Cloudflare Access: the wizard has a "Protect with Cloudflare Access" toggle — enable it. If prompted, pick a Zero Trust team name (free tier covers small teams).
  3. Add GitHub as an identity provider (Zero Trust → Settings → Authentication → Login methods → Add → GitHub): create a GitHub OAuth App (GitHub → Settings → Developer settings → OAuth Apps → New OAuth App) using the Authorization callback URL Cloudflare shows on this screen, then paste the Client ID/Secret back into Cloudflare.
  4. Set the Access policy on the application Cloudflare created for this project (Zero Trust → Access → Applications) to GitHub login only, with an Allow rule limited to the specific GitHub identities (or GitHub org) that should have access.

Once configured, every push to main redeploys automatically; visiting the site prompts a GitHub login and only approved accounts get through.
